# Souvenir 동시성 대응 메모

이 문서는 여러 Codex·ChatGPT 세션과 여러 사용자가 같은 Notion 워크스페이스에서 Souvenir를 사용할 때의 데이터 보호 계획을 기록한다.

## 목표

- 같은 설치·여행이 중복 생성되지 않게 한다.
- 오래된 읽기 결과가 최신 내용을 덮어쓰지 않게 한다.
- 네트워크가 끊겨 저장 여부가 불명확할 때 자동 재전송하지 않는다.
- 충돌을 숨기지 않고 사용자가 판단할 수 있는 변경안으로 보여준다.
- 디자인 원본과 사용 중인 여행 데이터를 서로 오염시키지 않는다.

## 적용 범위

| 영역 | 현재 경로 | 동시성 보호 수준 |
| --- | --- | --- |
| fallback 설치·여행 생성 | `notion_installer.py` | P0 구현 완료 |
| Python 계산 엔진 | `trip_engine.py` | 읽기 전용, 직접 쓰기 없음 |
| Codex·ChatGPT Notion 플러그인 쓰기 | 스킬 대화 규칙 | 재조회·단일 작성자 규칙 |
| 여러 컴퓨터의 분산 잠금 | 별도 coordinator 없음 | P2 대상 |

Python 엔진은 일정·예산·확인 화면을 계산만 한다. 계산 결과는 최신 Notion 상태를 다시 읽고 사용자 승인을 받은 뒤에만 쓰기 경로로 넘어간다.

## P0 · 기본 안전장치 — 구현 완료

### 1. 로컬 쓰기 잠금

`install`과 `scaffold`는 다음 두 잠금을 동시에 잡는다.

- 매핑 파일 잠금: 같은 `.souvenir-install*.json`의 중복 실행 차단
- 상위 페이지 잠금: 같은 Notion 상위 페이지를 대상으로 한 다른 매핑의 동시 실행 차단

잠금은 `O_CREAT | O_EXCL`로 원자적으로 생성한다. 잠금 파일에는 작업 ID, PID, 호스트, 작업명, 시작 시각을 남긴다. 오래된 잠금을 자동 삭제하지 않고, 실행 중인 프로세스가 없는지 확인한 뒤 수동으로 정리한다.

### 2. 불확실한 쓰기 중단

각 원격 변경 전에 `pending_operation`을 기록한다.

```json
{
  "key": "scaffold:itinerary:2",
  "operation_id": "...",
  "idempotency_key": "souvenir:...",
  "started_at": "..."
}
```

응답이 끊기거나 저장 여부를 확인하지 못하면 이 기록을 남긴 채 중단한다. 사용자가 Notion에서 결과를 확인하기 전에는 재전송하지 않는다.

### 3. 생성 멱등성

fallback DB에 내부용 `Souvenir 작업 키` 속성을 추가한다. 다음 행은 결정적인 키를 사용한다.

- 여행
- 일차별 일정
- 동행자
- 여행 지갑
- 준비할 일
- 준비물
- 기본 starter 행

생성 전에 같은 키를 조회해 한 건이면 재사용하고, 여러 건이면 충돌로 중단한다. 기존 fallback 설치에는 이 속성을 자동으로 추가한다.

### 4. 생성 후 검증

페이지·데이터베이스·행 생성 직후 생성된 ID를 다시 읽는다. 생성 응답은 받았지만 확인 읽기가 실패하면 성공으로 기록하지 않고 `UncertainWriteError`로 중단한다.

### 5. 낙관적 충돌 확인

속성 수정 API는 선택적으로 `expected_last_edited_time`을 받는다.

1. 저장 직전에 현재 페이지를 다시 읽는다.
2. 버전이 달라졌으면 `ConflictError`로 중단한다.
3. 저장 후 대상 페이지를 다시 읽어 결과를 확인한다.

같은 필드의 자동 병합이나 무조건적인 마지막 저장 우선 정책은 사용하지 않는다.

### P0 사용자 동작

```text
다른 Souvenir 쓰기 작업이 진행 중입니다.
현재 작업이 끝난 뒤 다시 시도하세요.
```

```text
페이지가 먼저 변경되었습니다.
최신 내용을 다시 읽고 변경안을 갱신한 뒤 반영할까요?
```

## P1 · 플러그인 쓰기 조정 — 다음 구현 단계

P0의 로컬 잠금은 한 컴퓨터 안에서만 공유된다. Notion 플러그인을 여러 기기에서 직접 호출하는 경우에는 아래 규칙을 추가한다.

### 1. 여행별 단일 작성자

동일 여행에는 한 번에 하나의 쓰기 배치만 허용한다.

```text
여행: 후쿠오카 여행
작업: 첫날 도착 시간 변경
작성자: Codex 세션 A
상태: 반영 중
만료: 10분 후
```

다른 세션은 확인 화면과 읽기만 수행하고, 첫 작업이 완료되면 다시 시도한다.

### 2. Notion 작업 기록

`Souvenir · 작업 기록` DB 또는 페이지에 다음을 기록한다.

- 여행 ID
- 작업 ID
- 작업자·세션 식별자
- 작업 종류
- 대상 행 ID
- 시작 시각·만료 시각
- `대기`·`반영 중`·`확인 필요`·`완료`·`충돌` 상태

Notion 페이지 자체는 완전한 원자적 잠금이 아니므로, 이 기록은 **조정용 lease**로 사용한다. claim 직후 다시 읽어 자신이 소유자인지 확인하고, 만료 전에도 쓰기 직전 재확인한다.

### 3. 필드 단위 변경안

전체 페이지를 덮어쓰지 않고 변경 속성만 보낸다.

- 다른 필드 변경: 병합 가능
- 같은 필드 변경: 충돌 표시 후 사용자 선택
- 사용자 메모·다른 날짜·기존 예약: 보존
- 수식·롤업: 직접 쓰지 않고 원본 입력만 수정

### 4. 쓰기 큐와 제한 처리

같은 워크스페이스의 쓰기는 순차 큐로 보낸다. 429 응답은 `Retry-After`를 따르고, 저장 여부가 불명확한 요청은 재시도하지 않는다.

### P1 테스트

- 서로 다른 플러그인 세션의 같은 여행 수정
- 같은 필드와 다른 필드의 동시 수정
- 작업 lease 만료·재획득
- 큐 대기 중 사용자가 취소
- 429·네트워크 단절·재연결
- 수식·롤업 반영 지연

## P2 · 분산 환경 확장 — 장기 과제

Notion API만으로는 여러 컴퓨터 사이의 강한 분산 잠금을 보장할 수 없다. 완전한 조정이 필요하면 Souvenir 전용 coordinator가 필요하다.

### 후보 구조

```text
Codex / ChatGPT / Claude
          │
          ▼
Souvenir MCP coordinator
          │
          ├─ 작업 lease·큐·멱등 키 저장소
          └─ Notion API
```

coordinator는 다음을 책임진다.

- workspace·trip별 단일 writer 보장
- lease heartbeat와 만료 복구
- 동일 `souvenir_key`에 대한 원자적 중복 방지
- 작업 재시작·취소·보상 처리
- 감사 로그와 충돌 이력

### P2에서 보장할 것

- 여러 기기에서 같은 여행의 동시 생성 직렬화
- 작업자가 오프라인이 된 뒤 lease 자동 회수
- 중복·충돌을 작업 단위로 되돌리는 보상 작업
- 버전별 템플릿 스키마 마이그레이션
- 원본 템플릿 배포와 사용자 여행 데이터 분리

## 충돌 처리 원칙

1. 모르면 덮어쓰지 않는다.
2. 저장 여부가 불명확하면 재전송하지 않는다.
3. 동일 작업 키가 여러 개면 임의로 선택하지 않는다.
4. 계산 결과보다 최신 Notion 원본 입력을 우선한다.
5. 사용자 메모·기존 예약·다른 날짜를 보존한다.
6. 충돌은 오류로 숨기지 않고 변경 전후로 보여준다.
