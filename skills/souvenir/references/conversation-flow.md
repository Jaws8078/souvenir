# Souvenir 대화형 계획 마법사

이 문서는 `$souvenir`가 한 번에 긴 설문을 던지지 않고, 사용자의 짧은 답을 받아 같은 여행에 순서대로 기록하기 위한 실행 계약이다. 실제 저장은 연결된 Notion 도구를 사용하고, 이 문서는 질문 순서·분기·보존 규칙을 정의한다.

## 실행 상태

대화가 이어지는 동안 아래 상태를 유지한다. Notion에는 비밀번호·쿠키·토큰을 저장하지 않는다.

```text
setup: notion_connection(unknown|connected|needs_user_action|unavailable) → account → workspace_id, workspace_name, workspace_confirmed → skill_active → login → template_status(unknown|found|needs_duplicate|duplicate_consent_pending|native_in_progress|browser_in_progress|manual_duplicate_wait|validating|confirmed|blocked) → template_source_url, template_page_id, template_page_url, template_confirmed
trip: trip_id, destination, start_date, end_date, duration_days,
      traveler_count, base_currency
plan: selected_parts, current_part, completed_parts
```

각 단계가 끝날 때 `Souvenir · 설치 기록` 또는 여행 요약 행의 상태를 갱신한다. 사용자가 중간에 멈추면 같은 `current_part`부터 재개하고, 이미 저장된 행은 제목·여행 키·원본 ID를 기준으로 재사용한다. `notion_connection`이 `needs_user_action` 또는 `unavailable`이면 여행 데이터 단계로 넘어가지 않고 연결 안내에서 멈춘다. `template_status`가 `confirmed`가 아니면 계획 파트 메뉴와 여행 데이터 단계로 넘어가지 않는다.

## 질문과 답변의 리듬

Souvenir는 긴 설문을 한 번에 던지지 않는다. 파트를 시작할 때 `question_fields`에 해당하는 최소 입력과 저장할 표만 한 줄로 알려주고, 이후에는 지금 필요한 항목 1~3개만 묻는다. 상세 `optional_fields`는 사용자가 원할 때만 펼친다. 이미 받은 값은 생략하고, 사용자가 바로 복사해 고칠 수 있는 자연스러운 예시는 한 개만 붙인다.

모든 사용자-facing 메시지는 아래 순서를 따른다.

```text
현재: <지금 단계>
<질문 또는 결과 한두 줄>
예시: <답변 예시 한 개>
다음 할 일: <사용자가 답할 내용·선택지·다음 확인>
```

예시가 필요 없는 완료·오류 메시지도 마지막 줄의 `다음 할 일:`은 반드시 남긴다. 질문을 여러 개 이어서 해야 할 때는 답변을 받은 뒤 다음 질문을 보낸다. 저장 전에는 변경 요약과 `반영 / 수정 / 건너뛰기`만 보여주고, 내부 ID·수식·API 처리 과정은 설명하지 않는다.

Google Places 검색도 같은 원칙을 따른다. 검색 진행 메시지에는 보안 설정이나 내부 인증 방식을 설명하지 않고, 현재 단계·검색 조건·후보 결과·사용자 선택지만 간결하게 보여준다.

오류·충돌·저장 여부 불명확 상태는 [오류와 예외 처리](error-handling.md)의 분류를 따른다. 오류가 난 단계 뒤의 작업은 멈추고, `확인 필요` 또는 `pending_operation`이 남은 쓰기는 Notion 실제 결과를 확인하기 전 재전송하지 않는다.

첫 실행의 연결 확인은 읽기 전용 Notion 요청 한 번으로 시작한다. 연결이 확인되면 `get_self({})`로 계정과 워크스페이스 ID·이름을 읽고, 이름을 항상 사용자에게 보여준 뒤 진행 확인을 받는다. 요청이 연결 UI를 반환하면 그 UI를 보여주고, 사용자가 승인했다고 답한 뒤 같은 요청을 한 번 재시도한다. 워크스페이스 이름을 읽지 못하면 연결된 것으로 처리하지 않는다. Souvenir가 다른 플러그인을 자동 설치하거나 사용자의 OAuth 승인을 대신한다고 설명하지 않는다.

## 고정 템플릿 선행 검사

워크스페이스 확인 직후 작업 메뉴보다 먼저 [고정 템플릿 게이트](template-gate.md)를 실행한다. 기준 설정의 링크·허용 제목·필수 섹션과 현재 워크스페이스의 유효한 설치 기록을 대조한다. 일치하는 복제본이 있으면 `template_status=confirmed`로 바꾸고 그 페이지의 구조·뷰·수식을 그대로 재사용한다. 없으면 먼저 복제 허락을 한 번 받고, CUA가 있으면 `browser_in_progress`, 네이티브 복제만 가능하면 `native_in_progress`, 둘 다 없으면 `manual_duplicate_wait`로 전환한다. 복제 후 실제 페이지 URL·ID·필수 섹션을 다시 확인하기 전에는 여행 행·일정·예산·예약을 만들지 않는다. 링크가 막혔거나 검사가 실패하면 `blocked`로 멈추며 청사진·다른 템플릿·빈 페이지로 우회하지 않는다.

## 시작 질문

고정 템플릿 검사가 `confirmed`가 된 새 사용자에게만 아래 한 줄을 보여준다.

```text
여행지 / 출발일 / 종료일 또는 기간 / 인원 / 기준 통화
예: 후쿠오카 / 2026-12-12 / 2026-12-15 / 4명 / JPY
```

목적지와 날짜 또는 기간이 있으면 바로 여행 요약 행을 만든다. 인원·통화가 미정이어도 멈추지 않는다. 날짜가 없고 기간만 있으면 `duration_days`와 `1일차…N일차`만 준비하고 실제 날짜는 비워 둔다. 템플릿의 `새 여행`·샘플 여행 행은 만들거나 보여주지 않고, 저장 직후 실제 목적지 이름의 행 하나만 남긴다.

저장 직후에는 사용자가 이해할 수 있는 자동 결과만 보여준다.

```text
여행 일수 4일 · 숙박 3박 · 1~4일차 준비 · 기준 통화 JPY
```

## 파트 선택

필수 정보가 저장되면 아래 8개를 한 번에 보여주고, 번호 여러 개 또는 `전부`를 허용한다.

1. 여행 개요·취향
2. 날짜별 일정
3. 항공
4. 숙소
5. 장소 보관함
6. 쇼핑
7. 예산·여행 지갑
8. 준비물·준비할 일

사용자가 선택하지 않으면 권장 순서인 `1 → 3 → 4 → 5 → 6 → 7 → 2 → 8`을 제시하고 1번부터 시작한다. 쇼핑은 선택 파트이며 필요 없으면 건너뛴다.
예시는 자연스럽게 한 줄만 붙인다. 예: `1, 3, 4 먼저` 또는 `전부`라고 답하면 돼요. 메뉴 메시지의 마지막 줄은 `다음 할 일: 번호 여러 개 또는 전부라고 답해주세요.`로 끝낸다.
사용자가 `나중에`, `보류`, `건너뛰기`라고 답한 파트는 지금까지 확인한 값만 저장하고 상태를 `미정` 또는 `확인 필요`로 남긴 뒤 다음 선택 파트로 이동한다. 사용자가 `다시`, `돌아가기`, `이어서`, `계속`이라고 하면 현재 여행의 미완료 파트 목록과 8개 메뉴를 다시 보여주고 번호 여러 개 또는 `전부`를 받는다. 예: `숙소는 나중에, 장소부터`처럼 답해도 된다.

## 공통 입력·저장 규칙

- 질문을 시작할 때 그 파트의 **최소 입력 필드 목록**을 먼저 보여준다. 전체 저장 필드는 상세 탭에서 확인할 수 있으며, 선택 필드는 사용자가 원할 때만 제시한다. 답변은 한 번에 한 사람·한 항목씩 받아도 된다. 모르는 값은 `미정`, 해당 없음은 사용자가 명시한 경우에만 `없음`으로 저장한다.
- 답변을 요구하는 질문에는 현재 목적지·일차·사람 이름을 반영한 짧은 **자연스러운 예시를 하나** 붙인다. 예시는 `[예시]`라고 표시하고 실제 입력과 섞지 않는다. 사용자가 그대로 복사해도 되지만, 예시 값은 사용자가 확인하기 전에는 절대 저장하지 않는다. `예/아니오` 질문도 `예: 아직 예약하지 않았어요`처럼 실제로 말할 법한 답을 함께 보여준다.
- 여러 필드를 한 번에 받을 때는 긴 가상 설문 대신 한 줄 예시를 사용한다. 이미 알려진 값은 예시에 다시 넣지 말고, 모르는 값은 `미정`으로 둘 수 있다는 안내를 덧붙인다.
- 시작 단계에서 받은 `목적지·출발일·종료일(또는 기간)·인원·기준 통화`를 모든 관련 행의 숨김 `여행 키`와 `여행` 관계에 함께 전달한다. 같은 값을 다시 묻지 말고, 각 파트를 시작할 때 현재 저장값을 짧게 확인한다.
- 이미 확보한 항공·숙소·동행자 취향·장소·예산을 다음 파트의 제안에 사용한다. 사용자가 답하지 않은 값은 추정하지 않고 `미정`으로 둔다.
- 사용자가 `미정`, `건너뛰기`, `없음`이라고 답하면 해당 속성을 비워 두고 상태를 `미정` 또는 `확인 필요`로 저장한다. 실제로 확인하지 않은 값을 `없음`, 0, 완료로 바꾸지 않는다.
- 작성 전에 기존 여행 키와 제목을 검색해 같은 행이 있으면 갱신하고, 새 행을 만들 때는 반드시 여행 키와 `여행` 관계를 연결한다. 대시보드·동행자·쇼핑·오늘/다음 일정 뷰도 같은 여행 키와 관계로 필터링한 뒤 실제 표시 행을 한 번 확인한다. 연결되지 않은 기존 여행을 보여주거나 링크만 걸어 두고 저장됐다고 말하지 않는다.
- 사용자가 링크·사진·파일을 주면 먼저 읽을 수 있는 정보만 추출한다. 원문을 확인하지 못한 값은 채우지 않고 `확인 필요`로 남긴다.
- 외부 검색 결과·예상 가격·운영 시간은 출처와 확인 시각을 함께 저장한다. 핵심 입력 저장을 외부 조회가 막지 않도록 먼저 `외부 확인 대기` 작업을 만들고, 호스트가 지도·웹·이미지 근거를 모은 뒤 한 번 사용자 확인을 받아 저장한다. 검색 결과만으로 예약·결제를 완료했다고 말하지 않는다.
- 항공권과 숙소 가격은 여행의 기준 통화와 관계없이 **KRW(원화)** 로 입력·표시한다. 원문이 엔화 등 다른 통화라면 확인된 환율 근거로 환산한 원화 금액을 입력하고, 근거가 없으면 자동 환산하지 않고 `확인 필요`로 남긴다.
- 여러 행을 바꾸는 파트는 저장 전에 변경 요약을 한 번 보여주고 `반영` 또는 `건너뛰기`를 받는다. 같은 여행 키·같은 DB를 여러 번 읽지 말고, 한 파트의 입력을 모은 뒤 한 번에 저장·검증해 대기 시간을 줄인다.
- 반영 후에는 대상 DB를 여행 범위별로 한 번 사전 조회해 작업 키를 재사용하고, 독립 행은 제한 병렬로 저장한다. 신규 행의 행별 즉시 재조회 대신 파트별 최종 조회로 실제 표시 행을 확인하며, 기존 행의 버전 충돌 검사와 멱등 키는 유지한다. 호스트가 느리거나 제한적인 경우 `SOUVENIR_WRITE_CONCURRENCY=1`로 순차 저장할 수 있다.

### Notion 반영 진행 브리핑

사용자가 `반영`을 승인한 뒤에는 결과가 나올 때까지 조용히 기다리게 하지 않는다. 실제 도구 호출 직전에 아래 단계를 현재 파트 이름과 함께 짧게 알린다. 이 메시지는 Notion의 내부 화면을 추측해 설명하는 것이 아니라, Souvenir가 지금 실행하는 작업을 알려주는 상태 안내다.

```text
1/4 입력과 후쿠오카 여행 연결을 확인하는 중…
2/4 숙소 DB와 기존 후보를 확인하는 중…
3/4 숙소 후보 3개를 Notion에 반영하는 중…
4/4 저장된 행과 화면 표시를 다시 확인했어요. 새 행 2개 · 수정 1개
다음 할 일: [항공 입력] [일정 입력] [여기서 종료]
```

- `1/4`는 현재 여행 페이지와 여행 키/관계가 맞는지 확인하는 단계다.
- `2/4`는 해당 파트의 DB와 같은 작업 키를 가진 기존 행을 찾는 단계다.
- `3/4`에서는 생성·수정·작업 잠금/lease를 처리하되, 사용자가 볼 필요가 없는 내부 토큰·ID·본문은 숨긴다.
- `4/4`는 저장 응답만 믿지 않고 여행 범위로 다시 읽어 관계·`구분=사용 중`·현재 뷰 표시 여부를 검증하는 단계다.
- `4/4`에서는 확인 존 연결도 함께 검증한다. 현재 파트의 행이 같은 여행 키로 확인 존의 오늘/다음 일정·예약·숙소·지갑·장소·쇼핑·준비·자료 요약에 연결되어야 하며, 연결 뷰에서 보이지 않으면 저장 완료로 처리하지 않는다.
- 한 파트가 여러 관리 DB로 나뉘는 경우(예산·지갑·사용 내역·정산, 항공·예약 등) 관련 행과 표시 카드가 모두 연결됐는지 확인한다. 일부만 보이면 누락된 파트만 재시도하고 기존 데이터는 다시 만들지 않는다.
- 외부 링크·사진·검색이 포함된 파트는 `지도 링크 확인 중…`, `후보 근거를 확인 중…`처럼 별도 상태를 먼저 보낸다. 확인이 끝나기 전에는 저장 중이라고 말하지 않는다.
- 충돌·권한·네트워크 오류가 나면 `3/4 반영 중단` 또는 `4/4 검증 중단`으로 알리고, 어떤 행도 완료됐다고 단정하지 않는다. 재시도 가능한지와 사용자가 해야 할 조치를 함께 보여준다. 오류 메시지의 마지막 줄에는 반드시 `다음 할 일: [다시 시도] [입력 수정] [중단]`을 붙인다.
- 반영이 끝나면 전체 여행 페이지 대신 실제로 바뀐 파트의 **블록 페이지 링크**만 먼저 보여준다. 데이터베이스 자체 URL·DB 뷰 URL은 사용자에게 보여주지 않는다. 새 여행 생성이 아닌 이상 여행 홈 링크도 기본 결과에 넣지 않는다.

대화에서 받은 값은 아래 표의 속성명으로만 저장한다. `질문 필드`와 `자동 결과`를 섞지 않고, 한 답변에 여러 의미가 들어오면 각 칸으로 분리한 뒤 저장 전에 요약을 보여준다. `의견·요청`처럼 의미가 섞인 단일 열은 새 입력에 사용하지 않는다.

```text
저장 전 변경 요약을 보여드릴게요. 반영할까요?
```

질문 예시: `숙소명과 1박 비용만 먼저 정하고 나머지는 미정으로 둘게요.`처럼 사용자가 실제로 답할 수 있는 문장을 한 개만 보여준다. 예시를 여러 개 나열해 사용자가 다시 선택하게 만들지 않는다.

Python 로컬 실행기를 지원하는 호스트는 `run_souvenir.py fields --part <파트>`로 위 계약을 읽고, `normalize_part_input`으로 답변을 DB별 행으로 정규화한다. 이 단계는 쓰기 전용이 아니며, Notion 저장은 반드시 사용자의 `반영` 뒤에 수행한다.

각 파트의 첫 질문은 엔진이 반환하는 `question_fields`만 사용한다. 전체 `fields`는 상세 입력과 저장 라우팅용이며, `optional_fields`는 사용자가 더 자세히 작성하겠다고 했을 때만 제시한다. 따라서 링크·사진·메모·상태·검증값이 비어 있어도 기본 행을 만들 수 있고, 자동 결과 속성은 질문하지 않는다.

## 1. 여행 개요·취향

여행 인원이 미정이면 먼저 인원 수만 묻는다. 인원이 `N명`이면 동행자 행을 정확히 N개 준비하고, 이름을 모르면 `동행자 1…N`을 수정 가능한 자리로 만든다.

사람별 입력은 한 사람씩 진행한다. 먼저 `동행자 1의 이름`을 받고, 이어서 역할·먹고 싶은 음식·선호 이동·숙소 취향·주의사항·추가 요청을 **각각 따로** 묻는다. 필요하면 담당 영역·개인 예산·예산 통화·메모도 같은 사람의 별도 필드로 받는다. 그 다음 동행자 2…N으로 넘어간다. 사용자가 한 번에 적고 싶어 하면 아래 한 줄 형식도 허용한다.

질문은 아래처럼 한 번에 하나씩 자연스럽게 이어간다.

```text
동행자 1의 이름은 어떻게 적을까요? [예시] 유성
이번 여행에서 맡을 역할은요? [예시] 예약 담당
먹고 싶은 음식이 있나요? [예시] 라멘, 모츠나베
선호하는 이동 수단은요? [예시] 지하철 위주
숙소에서 중요하게 볼 조건은요? [예시] 역에서 가깝고 조용한 방
주의할 점이 있나요? [예시] 견과류 알레르기
추가로 기억할 요청이 있나요? [예시] 늦은 밤 일정은 피하기
```

```text
이름 | 역할 | 먹고 싶은 음식 | 선호 이동 | 숙소 취향 | 주의사항 | 추가 요청
예: 유성 | 예약 담당 | 라멘, 디저트 | 지하철 | 역 근처·조용한 방 | 견과류 알레르기 | 늦은 밤 일정 제외
```

입력은 동행자 DB의 사람별 행에 저장한다. `역할`, `먹고 싶은 음식`, `선호 이동`, `숙소 취향`, `주의사항`, `추가 요청`은 서로 다른 텍스트 열에 각각 저장한다. 선택 태그 하나로 합치거나 `의견·요청` 한 칸에 여러 항목을 합쳐 넣지 않는다. 레거시 입력에 `의견·요청`만 있으면 자동으로 분해하지 않고 사용자에게 여섯 항목을 다시 요청한다. 역할은 반드시 이 동행자 행의 `역할` 열에 기록해 대시보드의 함께 가는 사람 표에서도 바로 보이게 한다. 여행 전체 방향·템포·가장 중요한 기준은 여행 요약 행에 한 번만 저장한다.

## 2. 날짜별 일정

여행 일수만큼 `1일차…N일차`를 차례로 준비한다. 날짜가 바뀌면 기존 일정의 날짜·일차를 다시 계산하되, 사용자가 쓴 일정명·메모·예약 연결은 보존한다. 기간이 늘어난 경우에만 빠진 일차를 추가한다.

일정 입력을 시작하기 전에 확정·후보 항공의 도착/출발 시각과 숙소 체크인을 요약한다. 늦은 도착이면 1일차는 공항 이동·체크인·휴식 중심으로 제안하고, 2일차부터 사용자가 하고 싶은 활동을 묻는다. 활동이 없으면 저장된 장소·취향·템포를 바탕으로 후보를 제안하며, 외부 검색이 필요할 때만 검색 동의를 받는다. 질문을 고정된 설문처럼 반복하지 말고 이미 알려진 정보에 따라 다음 질문을 줄인다.

각 일차는 아래 형식으로 짧게 받는다.

```text
일정명 | 시작-종료(선택) | 장소(선택) | 예약/메모(선택)
예: 공항 도착·체크인 | 14:00-16:00 | 후쿠오카 공항→숙소 | 이동 확인 필요
```

작성 후 `플랜 B를 만들까요? (예/아니오)`를 한 번 묻는다. 예라면 각 원래 일정 행의 `플랜 B`, 필요할 때 `플랜 C`만 채운다. 대안을 별도 활성 일정으로 만들지 않으며, 실제 적용은 영향 요약 뒤 사용자의 `반영`을 받아야 한다.
예: `비가 오면 수족관으로 바꿀까요?`처럼 해당 일정을 짚어 묻고, 사용자가 `네, 2일차만`이라고 답하면 그 일차에만 기록한다.

## 3. 항공

먼저 `이미 예약했나요? (예/아니오)`를 묻는다. 예: `네, 예약번호가 있어요` 또는 `아직 예약하지 않았어요`.

### 예약한 경우

텍스트·사진·파일 중 편한 방법을 받는다. 읽은 값은 다음 필드에 매핑한다.

```text
항공사 · 편명 · 가는 편 출발/도착 · 오는 편 출발/도착
공항/터미널 · 예약번호 · 좌석 · 수하물 · 체크인/탑승 마감 · 확인 링크
사진 또는 티켓 이미지: 첨부 파일은 `사진`, 원본 주소는 `사진 URL`
```

빠진 값은 한 번에 목록으로 보여주고 `입력 / 건너뛰기`를 받는다. 건너뛴 값은 `확인 필요`로 남긴다.
예: `좌석은 아직 모르니 건너뛰고, 수하물만 15kg으로 입력할게요.`

### 예약하지 않은 경우

```text
가는 편 선호 시간대 / 오는 편 선호 시간대 / 항공권 예산(KRW) / 출발 공항(선택)
예: 오전 8~11시 / 저녁 6시 이후 / 400,000원 / 인천공항
```

사용자가 검색을 승인하면 최신 웹 검색 결과를 출처와 함께 후보 DB에 기록한다. 후보는 예약 상태를 `후보`로 두고, 선택된 뒤에만 최종 항공 행과 공통 예약 행으로 복사한다. 선택 또는 예약 정보 반영이 끝나면 후보 목록은 보존한 채 `최종 항공` 요약 행을 추가·갱신한다. 실제 예약·결제·좌석 확보는 사용자가 항공사/예약 사이트에서 완료해야 한다.

## 4. 숙소

여행 개요에서 숙소 취향을 이미 받았는지 먼저 확인한다. 없으면 아래만 묻는다.

```text
지역/역 선호 · 1박 예산(KRW) · 필수 조건(침대·조식·세탁 등)
예: 하카타역 근처 · 120,000원 · 트윈 침대와 세탁기
```

후보는 텍스트·링크·사진으로 받는다. 각 후보에 아래 항목을 채운다.

```text
숙소명 · 주소 · 링크 · 사진 · 체크인/체크아웃 · 장점 · 단점 · 1박 비용(KRW) · 숙박 총액(KRW)
예: 하카타 리버 호텔 · 후쿠오카시 … · 공식 링크 · 15:00/11:00 · 역이 가까움 · 방이 작음 · 110,000원 · 330,000원
```

최종 선택 전 후보 비교를 보여주고, 선택 후에만 `숙소 상태=확정`과 예약 DB 연결을 반영한다. 기존 예약번호·메모·사용자 사진은 삭제하지 않는다.

## 5. 장소 보관함

파트를 시작할 때 먼저 이렇게 안내한다.

```text
5번 장소 보관함이에요.
가고 싶은 관광지·맛집·카페·쇼핑 장소를 여러 개 한 번에 적어주세요.
예: 오호리 공원 | 후쿠오카 | 관광 | 아침 산책
```

장소는 여러 개를 한 줄 목록으로 받아도 된다.

```text
장소명 | 지역 | 종류 | 링크/지도 URL | 사진 URL(선택) | 메모
예: 오호리 공원 | 후쿠오카 | 관광 | https://… | 아침 산책
```

Google Maps 일반 링크와 `maps.app.goo.gl`·`goo.gl/maps` 공유 링크를 모두 받을 수 있다. 공유 링크는 먼저 리디렉션된 최종 주소에서 장소명을 읽고, `/maps/place/...` 경로와 `query`·`q` 파라미터를 해석한다. 링크가 만료됐거나 열리지 않으면 호스트명(`maps.app.goo.gl`)을 장소명으로 저장하지 않고 `장소=확인 필요`와 `정보 상태=확인 필요`로 남긴다. 이 경우 사용자에게 장소명, 전체 Google Maps URL 또는 장소 화면 캡처 중 하나를 요청하고 확인 전에는 저장하지 않는다. 목적지와 맞지 않는 장소가 검색·지도 근거에서 확인되면 `불일치`로 표시하고 저장을 보류한다. 지역명이 모호하거나 근거가 없으면 `확인 필요`로 두며, 사용자가 명시적으로 승인한 장소만 `사용자 확인 완료`로 저장한다. 장소 카드에는 공식 링크·지도·사진·예산 메모·출처·확인일을 저장할 수 있으며, 실제 방문 완료와 일정에 담은 상태는 구분한다.

장소를 백지에서 찾는 경우에는 검색 결과를 추천순으로 **최대 10곳씩** 보여준다. 첫 화면에 10곳보다 적은 결과만 있으면 있는 만큼만 보여주며, 10곳을 넘으면 `조건에 맞는 다른 후보를 10곳 더 찾아볼까요?`라고 묻는다. 사용자가 `다음 10개`, `더 찾아줘`라고 답했을 때만 다음 묶음을 가져온다. 후보 번호·이름을 골라 저장을 요청하기 전에는 어떤 후보도 장소 DB에 쓰지 않는다. 검색 제공자가 추천 순위·평점·거리·운영 상태를 주면 후보 카드에 함께 표시하고, 다음 묶음에서도 이미 본 후보는 다시 보여주지 않는다.

로컬 실행기에 `GOOGLE_PLACES_API_KEY`가 설정되어 있고 사용자가 직접 검색을 원하면 `Google Places API (New) Text Search`를 사용한다. 키는 공개 플러그인에 내장하지 않고 환경변수로만 읽는다. 검색어는 `목적지 + 원하는 종류/조건`으로 만들며, 관련성/거리 정렬·장소 유형·영업 중·위치 반경을 선택할 수 있다. 후보 10개와 함께 평점·주소·지도 링크·공식 링크·영업 상태를 보여주되, 비용을 줄이는 요약 검색에서는 필요한 필드만 보여준다. 다음 요청에서는 Google이 반환한 페이지 토큰과 query·필터를 포함한 검색 세션을 함께 검증하며, 키와 토큰은 Notion에 저장하거나 사용자에게 노출하지 않는다. 키가 없거나 API를 사용할 수 없는 환경에서는 호스트의 웹·지도 검색 결과를 같은 후보 패킷으로 받아 처리한다.

사용자에게 보여주는 검색 안내는 다음처럼 짧게 유지한다.

```text
현재: Google Places 검색 준비
후쿠오카 카페 검색 조건을 확인했습니다.

다음 할 일: 검색 결과를 확인해주세요.
```

Google API 후보는 `Google Maps` 출처·검색 순위 안내·공식 로고 attribution을 붙여 검토 화면에서만 보여준다. 장소명·주소·평점·영업시간·사진·리뷰를 그대로 저장하지 않으며, 사용자가 Notion에 쓸 표시명을 직접 정한 경우에만 `place_id`(저장 예외)와 지도 링크를 함께 저장한다. 중복 장소명은 후보 번호나 `place_id`로 승인하고, 목적지 불일치 후보는 저장하지 않는다. 사진·리뷰를 표시하려면 작성자 attribution과 Google Maps 원문 접근 링크가 준비되어 있어야 하므로, 기본 검색에서는 사진·리뷰를 요청하지 않는다.

Notion 쪽은 `장소 후보 검토(임시)`와 `장소 보관함(정식)`을 같은 DB로 섞지 않는다. 후보는 채팅/호스트 패킷의 `후보 검토` 상태로만 머물고, 승인 전에는 행을 만들지 않는다. 승인 후 정식 행에는 `장소`, 사용자가 정한 `장소 ID`, `지도 URL`, `출처`, `정보 상태=사용자 확인 완료`만 우선 연결하며, 구형 복제본에는 `검색 제공자`와 `확인일` 속성을 자동으로 보완한다. 기본 화면은 `확인 완료 갤러리`로 필터하고, `검토 필요`는 직접 입력했지만 근거가 부족한 행을 따로 확인하는 용도로 둔다. 따라서 사용자는 검색 결과 표를 Notion에서 다시 관리하지 않고, 승인한 장소 카드만 장소 보관함·일정에 연결해 사용한다.

## 6. 쇼핑

쇼핑이 필요한지 먼저 한 번 묻는다. `아니오`, `없음`, `건너뛰기`면 쇼핑 DB와 진행 대상은 만들지 않고 다음 파트로 이동한다.
예: `이번에는 쇼핑 안 할게요` 또는 `사람별 선물 목록을 만들어요`처럼 답하면 된다.

쇼핑을 선택하면 여행 인원 수만큼 개인 목록을 준비한다. 사람별 품목 행은 실제 품목을 입력할 때 만들고, 비어 있는 `새 페이지`·예시 품목 행은 만들지 않는다. 공용 쇼핑 목록은 사용자가 필요하다고 확인한 경우에만 추가한다. 첫 질문에서 아래 네 가지를 한 번에 안내한다.

```text
품목명 · 가격(예상 총액) · 수량 · 구매 장소
예: 유자 킷캣 | JPY 1200 | 3개 | 하카타역 돈키호테
또는: 유자 킷캣 | 3개 | 하카타역 돈키호테 | JPY 1200
선택: 담당 여행자 · 사진(첨부 또는 URL) · 태그 · 결제 수단 · 링크/메모
```

사용자가 품목명만 주면 바로 저장하지 않는다. 목적지와 품목명을 검색어로 사용해 웹·이미지·제공 링크를 조사하고, 결과에서 가격·수량·구매 장소·태그를 찾는다. 후보마다 출처 URL과 확인 시각을 붙여 아래처럼 먼저 보여준다.

```text
후보 1 · 유자 킷캣
가격 JPY 1,200 · 수량 3개 · 구매 장소 하카타역 돈키호테
출처 https://example.com/item · 확인 2026-11-15
이 정보로 저장할까요?
```

사용자가 승인한 후보만 `정보 상태=사용자 확인 완료`로 사람별 쇼핑 DB에 저장한다. 가격·수량·구매 장소 중 하나라도 출처에서 확인되지 않으면 `확인 필요`로 남기고 저장하지 않는다. 저장 직후 현재 여행 키로 필터링한 목록을 다시 읽어 실제 품목 행이 화면 안에 펼쳐지는지 확인한다. 구매 장소가 장소 보관함에 있으면 장소 카드와 연결하고, 실제 구매가 끝난 금액만 `사용한 내역`에 연결한다. 예정 금액은 여행 지갑 잔액에서 자동 차감하지 않는다. 쇼핑을 선택한 경우에만 계획 목록과 진행도 대상에 포함하고, 끄면 기록은 보존하되 메뉴·집계에서 제외한다.

사진이 포함된 후보는 저장 직전에 `사진` 파일 속성과 `사진 URL`에 들어갈 값을 함께 보여준다. 첨부 파일은 호스트가 Notion에 업로드한 뒤 연결하고, 링크만 있으면 외부 파일로 연결한다. 사용자가 사진을 주지 않은 후보에 이미지를 임의로 만들거나 기존 사진을 교체하지 않는다.

## 7. 예산·여행 지갑

먼저 여행 인원 수를 확인한 뒤 사람별 준비 금액을 한 명씩 묻는다. 인원이 4명이면 개인 지갑/개인 예산 입력을 4개 준비한다. 이어서 공용 예산이 필요한지 묻고, 필요하다고 답한 경우에만 공용 지갑 행을 추가한다. 공용 예산이 필요 없으면 공용 행을 만들지 않는다.

```text
지갑 이름 / 통화 / 준비 금액
예: 공용 지갑 / JPY / 100000
```

개인 금액을 물을 때도 `유성 / JPY / 50000`처럼 답할 수 있다는 예시를 함께 보여준다.

사용자가 사람별 금액을 주면 사람별 지갑 또는 계획 예산 행으로 분리한다. 실제 지출은 `사용처·유형·단계·수단·금액` 다섯 칸만 받고, 지갑 잔액·사용률·통화 표시는 자동 결과로 둔다. 환율은 사용자가 확인한 값과 근거가 있을 때만 입력한다.

## 8. 준비물·준비할 일

기본 목록을 먼저 보여주고, 사용자가 `추가: …` 또는 `빼기: …`로 답하게 한다.

```text
기본 준비물 8개와 출발 전 할 일 15개를 준비했습니다.
추가하거나 제외할 항목이 있나요?
예: 우산과 보조배터리를 추가하고, 목베개는 빼주세요.
```

개인 준비물은 동행자와 연결하고, 공용 준비물은 대표 담당자와 수량을 둔다. 상태 변경만 진행률에 반영하며 구매 완료·수량 입력을 준비 완료로 추정하지 않는다.

## 완료 판정

진행 브리핑의 마지막 단계가 실제 재조회까지 통과한 뒤에만 아래처럼 완료 요약을 보여준다.

```text
✅ 여행 개요 저장 · 동행자 4명
🟡 항공 후보 3개 · 최종 선택 필요
⚪ 숙소 미정 · 후보 입력 대기
```

모든 파트가 끝나면 각 파트의 반영 링크, 자동 결과, `확인 필요` 목록, 다음에 할 수 있는 작업(예약 확정·일정 검사·준비 진행)을 보여준다. 전체 여행 링크는 사용자가 요청하거나 새 여행을 처음 만든 경우에만 함께 제공한다. 외부 예약·결제·최신 날씨·입국 요건은 자동 완료로 표시하지 않는다.
