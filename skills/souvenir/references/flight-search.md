# 항공권 웹 검색

예약하지 않은 항공편을 찾을 때 적용한다. 별도 API 가입이나 키 없이 호스트의 웹 검색과, 가능한 경우 브라우저 조작으로 조사한다. FlightAPI 가입·연결을 시작 조건으로 요구하지 않는다. 검색 기능이 실제로 제공되는지 먼저 확인한다.

## 조건 받기

여행의 목적지·출발일·종료일·인원은 재사용한다. 목적지 도시의 공항이 여러 개면 접근성을 비교하고 임의로 하나를 확정하지 않는다. 날짜가 없으면 특정 날짜의 가격 검색을 시작하지 않고 날짜 또는 검색 가능한 날짜 범위를 받는다.

추가로 필요한 것은 출발 공항, 가는 편·오는 편 선호 시간대, 항공권 예산(KRW)이다. 알고 있는 값은 생략하고 모르는 값은 `상관없음`·`미정`으로 받을 수 있다. 출발 공항은 거주지로 추정하지 않는다. 예산은 1인/일행 전체, 편도/왕복 기준을 확인하고, 소아·유아가 있다면 해당 검색에 필요한 인원 구성을 추가로 받는다. 수하물·직항 등 필수 조건은 이미 받은 요청을 재사용한다.

```text
현재: 항공 후보 찾기
출발 공항과 가는 편·오는 편 시간대, 예산을 알려주세요. 시간대와 예산은 미정이어도 괜찮아요.
예시: 인천 출발, 갈 때 오전·올 때 저녁, 1인 왕복 40만 원 이하로 찾아줘.
다음 할 일: 원하는 조건을 알려주세요.
```

사용자의 `찾아줘`는 검색 요청으로 처리하고 같은 검색 허락을 다시 묻지 않는다. 조건 입력만 끝난 경우 검색 진행 여부를 한 번 확인한다.

## 조사 순서

1. [네이버 항공권](https://flight.naver.com/)·[스카이스캐너](https://www.skyscanner.co.kr/flights)에서 후보를 탐색하고 [Google Flights](https://www.google.com/travel/flights/)를 보조로 사용한다. 매번 세 곳 모두를 순회하지 말고 접근 가능한 곳에서 조건에 맞는 결과를 확보한 뒤 유력 후보를 확인한다.
2. 검색 엔진은 해당 서비스와 항공사의 페이지를 찾는 데 사용한다. 검색 요약문, 광고의 `최저 ○원`, 월간 달력의 최저가를 지정 날짜·인원의 구매 가능한 가격으로 옮기지 않는다.
3. 브라우저 조작이 가능하면 노선·날짜·왕복 여부·인원·좌석 등급을 실제 검색 화면에 입력하고 결과를 읽는다. 출발·도착 공항, 날짜 변경, 다음 날 도착, 별도 발권·자가 환승 여부도 확인한다. 도구가 없으면 브라우저를 조작했다고 말하지 않는다.
4. 유력 후보의 항공사 공식 사이트 또는 해당 가격을 판매하는 실제 여행사 페이지에서 총액·수하물·요금 조건을 확인한다. 비교 사이트의 여행사 가격을 항공사 공식 판매 가격으로 표시하지 않는다. 항공사 일반 수하물 안내는 특정 운임의 포함 수하물 증거로 사용하지 않는다.
5. 사이트가 로그인·CAPTCHA·접근 차단을 요구하면 우회하지 않는다. 다른 접근 가능한 출처를 확인하고, 검증이 안 된 항목은 `확인 필요`로 둔다. 웹 검색만으로 실시간 검색 결과를 읽지 못하면 조건이 입력된 검색 링크(실제로 생성 가능한 경우) 또는 서비스 링크를 제공하고 캡처·예약 링크를 받아 이어간다. 검색 URL 매개변수나 결과 링크를 임의로 만들어내지 않는다.

진행 상황은 실제 수행에 맞춰 `항공 후보 검색 → 날짜·인원별 판매가 확인 → 수하물·조건 비교 → 선택한 후보 저장 → 확인 존 연결 점검`으로 짧게 알린다.

## 후보 비교

조건을 충족하는 확인 가능한 후보를 먼저 보여준다. 추천순은 필수 조건 충족을 우선하고, 선호 시간대·환승 부담·확인된 총액을 함께 고려해 이유를 한 줄 적는다. 가격순 요청이면 동일한 인원·왕복 범위·수하물 조건으로 비교할 수 있는 후보끼리 정렬한다. 미확인 금액을 0원으로 취급하거나 예상 왕복 요금을 편도 두 배로 만들어내지 않는다. 같은 편을 판매사만 달리해 별개 항공편처럼 늘리지 않는다.

후보 수에 상한을 두지 않고 검색에서 확인한 조건 충족 항공편을 모두 제시한다. 추천순은 표시 순서이며 하위 후보를 제외하는 기준이 아니다. 접근 가능한 검색 결과의 다음 페이지·추가 결과도 확인하고, 같은 항공편의 판매처별 요금은 한 후보 아래에 묶는다. 왕복은 조건을 충족하는 실제 판매 조합별로 비교하며 서로 다른 시간·편명 조합을 임의로 합치지 않는다. 결과가 많으면 시간대별 표나 연속 메시지로 나눠 끝까지 보여주고, 추가 후보 표시를 위해 `더 볼까요?` 승인을 반복하지 않는다. 사용자가 중단하거나 범위를 좁히면 그 요청을 따른다.

검색한 사이트·날짜·인원과 확인한 후보 수를 함께 밝힌다. 사이트의 결과 제한·접근 차단·미확인 페이지가 있으면 조사 범위를 표시하고 전 세계 모든 판매처의 항공권을 빠짐없이 확인했다고 주장하지 않는다. 조건 충족 여부가 미확인인 결과는 `확인 필요 후보`로 분리해 보여주고 확정 조건 충족 건수에 포함하지 않는다. 조건에 맞는 결과가 없으면 조건 완화는 사용자 선택을 받는다. 장소의 기본 10개 규칙을 항공에 적용하지 않는다.

| 표시 항목 | 기록 기준 |
|---|---|
| 항공사·편명 | 마케팅/실제 운항사가 다르면 함께 표기. 미확인 편명은 추정 금지 |
| 가는 편·오는 편 | 공항, 현지 출발·도착 날짜와 시각, 다음 날 도착 여부 |
| 직항·경유·소요 시간 | 경유지, 환승 시간, 별도 발권 여부를 확인한 범위에서 표시 |
| 가격 | KRW, 1인/일행 전체, 편도/왕복, 인원·좌석 등급, 세금·수수료 포함 여부 |
| 수하물·조건 | 해당 운임의 기내/위탁 수하물, 변경·취소 조건. 미확인은 `확인 필요` |
| 근거 | 비교 출처와 실제 판매처 링크를 구분하고 조회 일시·시간대 표시 |

원화 가격이 없으면 원문 금액·통화와 확인된 환율의 기준 시점을 보존한다. 환율 근거가 없으면 KRW 요금은 비워 두고 `확인 필요`로 표시한다. 예상 환산액은 확정 결제액과 구분한다. 실시간 판매 페이지를 확인하지 못한 결과는 `노선·시간 후보 / 가격 확인 필요`로만 제시하고 `최저가`·`좌석 확보`·`예약 가능 확인`으로 표현하지 않는다.

## 선택과 Notion 저장

- 비교 결과를 먼저 제시한 뒤 저장할 후보를 받는다. `2번 저장해줘`처럼 명확한 요청이면 같은 저장 승인을 반복하지 않는다. 후보 저장은 예약 확정이 아니다.
- [데이터 운영 규칙](data-operations.md)에 따라 현재 복제본의 실제 항공 스키마에 저장한다. 왕복 후보는 공통 후보 식별자를 본문에 남기고 가는 편·오는 편을 연결한다. 왕복 총액은 후보 전체 기준으로 한 번만 기록하며 각 구간에 총액을 중복 배분하지 않는다.
- `항공권 예산`에는 사용자의 예산만 넣는다. 조회한 가격을 예산 열에 덮어쓰지 않는다. 별도 요금·금액·금액 범위 속성이 있으면 실제 의미에 맞춰 사용하고, 없으면 항공 후보 행 본문에 구조화해 기록한다. 출처·조회 시각·수하물·가격 범위도 전용 속성이 없으면 같은 본문에 남긴다. 단순 표시를 위해 DB를 새로 만들지 않는다.
- `확인 링크`에는 검증한 해당 후보의 판매 링크를 우선 저장한다. 일반 검색 링크밖에 없으면 본문에 `검색 링크·가격 미확인`으로 구분한다. 재실행은 기존 후보 행을 갱신하며 기존 예약번호·티켓·메모를 보존한다.
- 후보 상태는 `후보`·`비교 중`, 사용자 선택 후 `선택`으로 설정한다. 예약하지 않은 선택은 `최종 항공` 화면에 `선택·예약 전`으로 표시하고, 예약 확정 집계·예약 완료·지출 차감을 발생시키지 않는다. 실제 예약 증빙을 받은 뒤에만 예약 완료와 공통 예약 행을 갱신한다.
- 같은 여행 관계와 후보/선택 상태를 연결해 항공 파트의 실제 표·카드, 여행 중 확인 존에 보이는지 재조회한다. 필터·관계 문제로 보이지 않으면 완료라고 하지 않는다. 완료 메시지에는 항공 파트 블록 페이지 링크와 다음 행동을 제시하며 DB 자체 URL은 보여주지 않는다.

## 검증 범위

이 절차는 호스트 도구로 수행하는 스킬 동작 규칙이다. 독립적인 가격 수집기나 상시 가격 추적을 구현한 것으로 설명하지 않는다. 실제 사이트 검색·판매가 대조·Notion 반영은 해당 실행에서 확인한 범위만 완료로 보고한다.
